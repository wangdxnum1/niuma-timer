## 0. 背景与目标

### 0.1 为什么做这一包

前三轮迭代（v1.1.0 ~ v1.3.0）把功能堆到了一个相当的高度：周账单、数据洞察三视图、守护提醒、远程会话识别、存储治理。但**用户对自己的数据只有「看」的能力，没有「拿」和「还」的能力**：

- 数据全部在 `%APPDATA%\niuma-timer\`（SQLite `niuma.db` + `config.json`）—— 换机、重装、库损坏时**没有任何内置的导出/还原入口**，只能靠用户自己摸到 AppData 里拷文件。这是数据主权问题，不是功能问题。
- `export_csv` 只导出「账单 / 加班明细」这类**业务视图**，导不出**完整可还原的数据**。
- README 停在 v1.1.0 两天前，此后 v1.2.0 / v1.3.0 两大轮的功能（账单、热力、趋势、身体账单、守护提醒、托盘悬停卡、AUMID 通知修复）**一项都没写进文档**；仓库门面与产品实际能力严重脱节。
- 三处明确欠下的技术小债长期挂着（详见 0.3）。

本包的目标是**让用户能把自己的数据完整取走、完整放回**，并把仓库门面与三处小债一并结清——它是三包里唯一「不新增功能惊喜、但显著降低长期风险」的一包。

### 0.2 关键事实核对（动笔前已逐条查证，避免设计踩空）

| 事实 | 查证结果 | 对本设计的影响 |
| --- | --- | --- |
| 数据落点 | `config::config_dir()` = `dirs::config_dir()/niuma-timer`，即 `%APPDATA%\niuma-timer`；库文件 `niuma.db`（WAL 模式，另有 `-wal` / `-shm`）；配置 `config.json` | 备份只需打包 `niuma.db` + `config.json` 两个业务文件；图标缓存 / 日志 / panic.log 均**可再生或不属数据**，不打包 |
| DB 连接生命周期 | `db::conn()` 是 `OnceLock<Mutex<Connection>>`，**进程内永不释放**；托盘常驻全程持连接 | 不能「拷文件」：直接 `fs::copy` 覆盖 `niuma.db` 会与已打开的连接冲突。备份侧用 `VACUUM INTO` 取一致性快照；还原侧必须走「下次启动交换」 |
| WAL 一致性 | 库开 WAL，写可能尚未 checkpoint 进主库文件；直接拷 `niuma.db` 会**丢最近的写入** | `VACUUM INTO` 由 SQLite 保证快照一致，`-wal`/`-shm` 无需单独处理（这是选它而不是 `checkpoint + copy` 的原因） |
| 配置是否有退出时回写 | `config::save()` 只在 `main.rs` 的 `save_config` 命令（L214）调用；`RunEvent::Exit` 只 flush 活动统计，**不写 config.json** | 还原时可以直接覆盖 `config.json`，不存在退出时被内存态覆盖回去的风险 |
| 应用能否自我重启 | `tauri::AppHandle::restart(&self) -> !`，已在本地 `tauri-2.11.5/src/app.rs:588` 确认存在 | 还原后可以自动重启，用户无需手动重开 |
| 现有「写文件」范式 | `export_csv` 走 `dirs::download_dir().or_else(document_dir)` + 文件名安全清洗 + 返回最终路径给前端提示 | 备份沿用同一范式（同样的目录选择与路径回传），风格一致 |
| 现有依赖 | `Cargo.toml` **无** `zip` / `flate2` / `sha2` 等；`reqwest` / `rusqlite` / `dirs` / `serde` 已有 | 需新增 `zip` 一个依赖（见 §1 决策表） |
| 命令名单双向校验 | `scripts/test_commands.js` 已做双向断言：① 每个 `#[tauri::command]` 都要在 `capabilities/default.json` 有对应 `allow-*`；② capabilities 里每条 `allow-*` 都要有真实命令 | 删命令 / 改命令名后**陈旧权限项会被自动点名**，不必新写守卫 |
| `build.rs` 的 `sync_capabilities` | **只增不删**：仅在缺失时插入 `allow-<kebab>`，从不清理 | 删命令后**必须手工删除** `allow-pause-monitor`，否则编译通过、测试才报错 |
| README 现状 | `README.md` 是**英文**、`README.zh-CN.md` 是**中文**，两份都停在 **1.1.0（2026-09-18）**；两份互相链接、都链 CHANGELOG | 双语结构已存在，本包只做「同步 + 加校验」，**不新增 `README_EN.md`**（见 §1 决策表） |
| 前端测试注册方式 | `scripts/run_all.js` 自动 `readdirSync` 收集 `scripts/test_*.js` 并在子进程逐个跑 | 新增断言脚本**零注册成本**，`build.bat test` 自动纳入 |
| 设置页缩进 | `frontend/index.html` 中 `viewSettings` 块（含注释）整体比 `viewBill` / `viewOt` / `viewAct` / `viewApp` / `viewAudio` **少 4 个空格**，块内元素也同步少 2 空格 | 纯空白修正，不动任何标签 / ID / 文本 |

### 0.3 「三个小债」的准确清单

| # | 债 | 事实依据 |

### 0.4 目标（可验收）

1. 设置页一键生成**完整数据备份**（单一 zip，含库 + 配置 + 清单），落到用户 `文档\niuma-timer-backup\`，界面显示最终路径与大小。
2. 设置页列出备份目录下全部备份（时间 / 版本 / 大小），一键还原；还原**前自动为当前数据做一份保护性备份**，还原**校验通过**才落盘，落盘后**自动重启生效**。
3. 两份 README 同步到 v1.4.0 的真实能力，并有一条机器可校验的**双语一致性守卫**，此后发布不会再出现「文档落后两个版本」。
4. 三处小债清零。

### 0.5 非目标（明确不做，避免范围蔓延）

- **不做云同步 / 网盘上传**——备份就在本地磁盘，用户想同步自己挪。
- **不做定时自动备份**——本轮只做「手动一键 + 还原前自动保护」。理由：定时任务的失败路径（磁盘满 / 权限）需要通知、重试、保留策略一整套，与本包「低风险结账」的定位不匹配。
- **不做备份加密 / 密码**——加密会引入「密码丢了数据就没了」的不可逆风险，且本机数据本身已是明文。
- **不做增量备份**——单库体积实测在亚 MB 级（v1.1.0 实测主库 248KB），全量 zip 的代价可以忽略。
- **不迁移历史 `docs/plans/`**——本轮 spec 落在 `docs/superpowers/specs/`，历史目录原样保留（三份 spec 一致口径）。
- **不做「还原单个日期区间」**——只做整库还原。

## 1. 决策表

| 决策点 | 结论 | 理由 / 代价 |
| --- | --- | --- |
| 备份内容 | `niuma.db` 一致性快照 + `config.json` + `manifest.json`，打成单一 zip | 用户裁决「db+配置打包 zip」。图标缓存可从 exe 重提取、日志是诊断产物，均不入包 |
| 库快照方式 | `VACUUM INTO '<临时文件>'`，**不是** `checkpoint + 拷贝主库文件` | 唯一能保证「含未 checkpoint 的 WAL 写入且文件级一致」的方式；避免备份到半截的库 |
| zip 实现 | **引入 `zip` crate**（`default-features = false`, `features = ["deflate"]`） | 用户裁决。手写 store-only zip 要自研 CRC32 + 本地头 + 中央目录，格式兼容风险留在自己手里 |
| 备份落点 | `dirs::document_dir()/niuma-timer-backup/`（取不到文档目录时退回 `config::config_dir()/backups`） | 用户裁决「文档\niuma-timer-backup\」。放文档目录用户摸得到，放 AppData 等于没给 |
| 备份文件命名 | `niuma-backup-v{版本}-{YYYYMMDD-HHMMSS}.zip` | 时间戳天然去重且可排序；带上写入时的应用版本便于还原时判断代差 |
| 还原选文件 | **内置备份列表**：列出默认备份目录下的 `*.zip`，点击即还原 | 用户裁决。不引入 `tauri-plugin-dialog`、不加 `dialog:default` 权限，与本项目「零对话框」风格一致。代价：用户自己挪走的备份无法在界面里选（写进 hint 说明） |
| 还原校验 | ① zip 可读且含 `manifest.json` / `niuma.db`；② 清单 JSON 可解析；③ 解出的库以**只读连接**打开后 `PRAGMA integrity_check` 返回 `ok`；④ 7 张业务表齐全 | 校验不足会把用户唯一一份数据换成半截文件；`integrity_check` 在亚 MB 库上开销可忽略（一次性操作） |
| 还原前保护 | **强制**先自动备份当前数据；该步失败则**中止还原** | 「还原」是唯一会覆盖用户唯一数据副本的操作，必须有回退点。失败即中止而不是「问用户要不要继续」——多数用户会点继续 |
| 还原落盘方式 | **两段式**：解压到 `niuma.db.pending` / `config.json.pending` → 自动重启 → **下次启动最开头**做文件交换 | 进程持着 DB 连接，当场覆盖 `niuma.db` 不安全（详见 §2.2）。这是本包唯一有并发风险的设计点 |
| 交换位置 | `main()` 最开头，与包 A 的 `--apply-update` 助手拦截**同一区域**（在 `install_crash_log()` 之前、`db::conn()` 之前） | `db::conn()` 在 `.setup()` 里首次调用；必须在它之前完成交换，否则交换的是一个已被打开的库 |
| 交换失败处置 | 尽力回滚（`.pre-restore.bak` 改回原名），写 `debug.log`，**继续正常启动** | 还原失败绝不能让程序起不来——那会把「可恢复的问题」变成「用不了的程序」 |
| 旧库留存 | 被换下的旧库改名为 `niuma.db.pre-restore.bak`（单份，覆盖式） | 给最后一层手工救援通道；不按时间戳堆多份，避免 AppData 无限增长 |
| 自动重启 | 还原落 pending 后延迟约 800ms 调 `app.restart()` | 给前端留出「还原成功，正在重启…」的渲染时间；`restart()` 返回 `!`，调用后不再有后续代码 |
| 备份目录是否可配 | **不新增配置项** | 固定路径 + 界面显示实际路径即可；可配会带来「配置的目录不存在 / 已删除」的额外失败态 |
| 新增配置项 | **零** | 备份列表自带时间戳，无需 `backup_last_at`；还原是即时动作，无需持久化状态 |
| README 结构 | **维持现状**：`README.md`（英）+ `README.zh-CN.md`（中），两份都同步到 1.4.0 | 用户裁决。英文版已存在，新增 `README_EN.md` 只会造出三份两两重复的文档 |
| 双语校验落点 | 新增 `scripts/test_readme.js`，由 `run_all.js` 自动纳入 `build.bat test`；`release.bat` 第 0 步就是 `build.bat test` | 用户裁决「发布前双语校验」。零脚本改动即达成「发布前必过」 |

## 2. 后端改动

### 2.1 依赖：`src-tauri/Cargo.toml`

```toml
# 备份打包：只用 deflate，不拉 bzip2/zstd/aes 等无用的传递依赖
zip = { version = "2", default-features = false, features = ["deflate"] }
```

> 关闭默认特性是刻意的：`zip` 的默认特性集会带入 `bzip2` / `zstd` / `aes-crypto` / `time` 等，本项目只写 deflate 单一格式，多拉的每一个 crate 都是发布产物体积与编译时间。

### 2.2 新模块：`src-tauri/src/backup.rs`

模块文档（文件头注释）需写清两件事：
1. **为什么用 `VACUUM INTO`**：库开 WAL，最近的写可能还在 `-wal` 里没并进主库文件；`VACUUM INTO` 由 SQLite 自己产出一份「已合并 WAL、页级一致」的新库文件，是唯一可靠的文件级快照手段。
2. **为什么还原要两段式**：`db::conn()` 是进程级 `OnceLock`，连接永不释放；在持连接的状态下用 `fs::copy` 覆盖 `niuma.db`，Windows 层面可能成功，但已打开的连接持有的是旧页缓存，后续读写会把**新旧数据混在一起**——这是最难排查的一类数据损坏。因此还原只做「铺好 pending 文件」，真正的替换发生在**下一个进程的最开头**，此时还没有任何连接。

#### 2.2.1 数据结构

```rust
/// 一份备份在界面上的呈现（列表项），字段全部来自 manifest.json + 文件自身
#[derive(Debug, Clone, serde::Serialize)]
pub struct BackupEntry {
    /// zip 文件名（还原时作为定位键；不含路径，避免前端拼路径）
    pub name: String,
    /// 完整绝对路径（界面提示用）
    pub path: String,
    /// 文件字节数
    pub bytes: u64,
    /// 备份创建时刻，本地时区 `YYYY-MM-DD HH:MM:SS`
    pub created_at: String,
    /// 写入该备份时的应用版本（可能低于当前版本；界面据此提示「此备份来自 vX.Y.Z」）
    pub app_version: String,
    /// 若 zip 读不出清单（被截断 / 非本应用产物），置 true，界面标「不可用」
    pub broken: bool,
}

/// 打进 zip 的 manifest.json，同时是还原时的第一道校验依据
#[derive(Debug, Clone, serde::Serialize, serde::Deserialize)]
pub struct Manifest {
    /// 固定 "niuma-timer"，用于识别「这不是本应用的备份」
    pub app: String,
    pub app_version: String,
    pub created_at: String,
    /// 快照库文件的字节数（还原时与解出的文件比对，防止 zip 内条目被换掉）
    pub db_bytes: u64,
    /// config.json 是否存在（用户可能删过配置，允许缺失）
    pub has_config: bool,
}
```

#### 2.2.2 函数签名

```rust
/// 备份目录：文档\niuma-timer-backup；取不到文档目录时退回 %APPDATA%\niuma-timer\backups
pub fn backup_dir() -> PathBuf;

/// 生成一份备份。步骤：
///   1. create_dir_all(backup_dir)
///   2. 临时快照库落 config_dir()/backup-snapshot.db（先删残留），`VACUUM INTO` 写入
///   3. 组 zip：manifest.json / niuma.db（deflate）/ config.json（存在才写）
///   4. 删临时快照；返回 BackupEntry
/// 库开不出来 / 写 zip 失败 → Err(中文原因)，调用方直接展示
pub fn create_backup(cfg_version: &str) -> Result<BackupEntry, String>;

/// 列出备份目录下的全部 *.zip，按 created_at 倒序（新→旧）。
/// 读不出 manifest 的条目 broken=true 但仍然列出——用户需要看到「这里有个坏文件」
pub fn list_backups() -> Vec<BackupEntry>;

/// 读出 zip 内的 manifest.json（只读中央目录 + 一个条目，不整包解压）
pub fn read_manifest(zip: &Path) -> Result<Manifest, String>;

/// 还原第一步：校验 + 铺 pending 文件。
/// 校验链见 §1 决策表；任一环失败即 Err 且**不产生任何磁盘副作用**。
/// 校验通过后：
///   a. 先 create_backup()（保护性），失败则 Err 中止
///   b. 解压 niuma.db   → config_dir()/niuma.db.pending
///   c. 解压 config.json → config_dir()/config.json.pending（zip 内无则跳过）
/// 返回给界面的一句话摘要（含保护性备份文件名）
pub fn stage_restore(name: &str, current_version: &str) -> Result<String, String>;

/// 还原第二步：启动期交换。在 main() 最开头调用，**先于 db::conn() 的一切调用**。
/// 无 pending 文件 → 立即返回 None（零开销）。
/// 有 → 交换 → 返回 Some(摘要) 供写日志。失败尽力回滚并返回 None。
pub fn apply_pending_on_startup() -> Option<String>;
```

#### 2.2.3 `create_backup` 的关键实现约束

```rust
// 临时快照必须先删：VACUUM INTO 对已存在的目标文件会直接报错
let snapshot = config::config_dir().join("backup-snapshot.db");
let _ = std::fs::remove_file(&snapshot);
// 路径里的单引号在 SQL 字面量里要转义，否则 VACUUM 直接语法错
let sql = format!("VACUUM INTO '{}'", snapshot.to_string_lossy().replace('\'', "''"));
```

- 必须在 `db::with_db` 提供的连接上执行（统一处理锁中毒与错误上报，不复用 `conn().lock().unwrap()`）。
- zip 内的条目名**固定为 `manifest.json` / `niuma.db` / `config.json`**（不带目录前缀），还原侧按名精确查找。这样 zip 用任何解压工具打开时结构一眼可读。
- 临时快照用完即删；**即使中途 `Err` 也要删**（用 `Drop` 守卫或显式在错误分支删除），否则会在 AppData 里留下一个和主库等大的垃圾文件。

#### 2.2.4 `apply_pending_on_startup` 的交换顺序与回滚

```
输入：config_dir() 下是否存在 niuma.db.pending

1. 无 pending                                → return None
2. 删 niuma.db-wal / niuma.db-shm            → 旧连接留下的日志对新库是污染
3. niuma.db 存在？ → rename → niuma.db.pre-restore.bak（覆盖旧的）
4. rename niuma.db.pending → niuma.db
   失败 → 把 .pre-restore.bak 改回 niuma.db，写日志，return None
5. config.json.pending 存在？
   → config.json 改名 .pre-restore.bak → pending 改名 config.json
   失败 → 仅回滚 config（库已就位，不回退——回退库反而更糟：那会把刚还原的库又换成旧的）
6. 写 debug_log：应用了哪份备份、旧库留在哪
7. return Some(摘要)
```

> **第 5 步的非对称处置是刻意的**：库是数据的全部，配置只是偏好。库已成功就位后，为了一份配置把库回滚成旧的，等于让用户白等一次重启还什么都没还原。配置失败就让它失败（下次启动用默认配置，用户重设即可），并且**必须写日志解释为什么配置没换过来**。

#### 2.2.5 命令层（`src-tauri/src/main.rs`）

```rust
/// 立即生成一份备份（设置页按钮）
#[tauri::command(async)]
fn backup_now() -> Result<backup::BackupEntry, String>;

/// 列出备份目录下的全部备份
#[tauri::command(async)]
fn list_backups() -> Vec<backup::BackupEntry>;

/// 还原指定备份：校验 + 铺 pending 成功后再延迟重启。
/// 注意：本命令**成功返回后进程才会退出**——前端拿到 Ok 先渲染提示，800ms 后进程重启。
#[tauri::command(async)]
fn restore_backup(app: tauri::AppHandle, name: String) -> Result<String, String>;
```

- 三个命令都标 `(async)`：`create_backup` 要做 `VACUUM INTO` 全库重写 + deflate 压缩；`stage_restore` 要做 `integrity_check` + 解压。理由与既有 `get_storage_info` 完全一致（见其文档注释：同步 command 默认在主线程执行，会冻结托盘 1s 刷新）。
- **`backup_now` 不需要 `State<AppState>`**：清单里的版本号取 `env!("CARGO_PKG_VERSION")`，不需要读配置。少一个状态依赖就少一处锁竞争。
- `restore_backup` 的重启实现：

```rust
let handle = app.clone();
std::thread::Builder::new()
    .name("niuma-restore-restart".to_string())
    .spawn(move || {
        std::thread::sleep(std::time::Duration::from_millis(800));
        handle.restart(); // -> !，调用即进程重入，不返回
    })
    .map_err(|e| format!("重启线程创建失败：{e}"))?;
```

## 10. 风险与降级

| 风险 | 影响 | 缓解 / 降级 |
| --- | --- | --- |
| 还原路上任一环失败 | 用户唯一数据被覆盖 | 强制保护性备份 + 校验通过才铺 pending + 两段式交换 + `.pre-restore.bak` 兜底 + 失败不回滚库（§2.2.4） |
| `zip` crate 传递依赖变大 | 发布体积 / 编译时间 | `default-features = false` 只留 deflate；实测体积影响在百 KB 级，可接受 |
| `VACUUM INTO` 在大库上耗时 | 界面卡顿 | 命令标 `(async)`；界面在等待期显示「正在打包…」并禁用按钮 |
| 磁盘满 / 文档目录被 OneDrive 重定向后不可写 | 备份失败 | `create_backup` 返回可读中文原因；`backup_dir()` 退回 `%APPDATA%\niuma-timer\backups` 作为降级落点 |
| `app.restart()` 在某些环境失效 | 用户看不到还原生效 | 前端遮罩文案补一句「若 10 秒内未自动重启，请手动退出并重新打开」；重启失败不影响已铺好的 pending 文件（手工重启照样生效） |
| 双语校验误报（新增章节只加一份） | 发布被自己挡住 | 这正是设计意图。误报的处置成本是「补另一份文档」，漏报的成本是「用户看错文档」 |
| 包 A / 包 B 也在改 `capabilities/default.json` 与 README | 合并冲突 | 三包同版发布、同一分支顺序落地：先 B（改命令名）、再 A（加更新命令）、最后 D（删死命令 + README）。每步都跑 `build.bat test` |
| `main()` 开头块的顺序写反（helper 拦截 vs pending 交换） | 助手模式下白做一次交换 | §2.3 已明确约定顺序；落地时在该区域加注释固定 |
