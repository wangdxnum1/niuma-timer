## 修复：Raw Input 键盘事件被静默丢弃 → 按键次数恒为 0（提交 5a82304）

用户反馈「方案 B 之后输入法不卡了，但按键次数是 0」。排查结论：

**根因**：`activity.rs::raw_wndproc` 的缓冲区门槛 `buf.len() >= size_of::<RAWINPUT>()`。
`GetRawInputData` 返回按设备浮动的字节数，而 `size_of::<RAWINPUT>()` 取 union 最大分支恒为 48（x64）：

| 事件 | 实际 cb | 组成 |
| --- | --- | --- |
| 键盘 dwType=1 | **40** | header 24 + RAWKEYBOARD 16 |
| 鼠标 dwType=0 | **48** | header 24 + RAWMOUSE 24 |

40 >= 48 恒 false → 每个键盘 WM_INPUT 都被无声丢弃；鼠标 48 恰好通过。
注册本身成功，所以表现是「鼠标有数、按键恒 0」；「输入法不卡」只说明低端钩子已拆。

**验证手段（可复用）**：写 Python ctypes 探针（临时目录，未入库）——建 message-only 窗口 +
`RIDEV_INPUTSINK` 注册 + `SendInput` 注入 + `PeekMessageW` 泵 5 秒，打印每个 WM_INPUT 的
(dwType, cb)。实测确认键盘 40 / 鼠标 48。注意：必须显式设 argtypes/restype（否则 x64 句柄被截断），
`PeekMessageW` 是 5 个参数，`sizeof(INPUT)` = 40。

**修复**：
- `win.rs::read_raw_input`：缓冲改 `max(cb, size_of::<RAWINPUT>())` 零填充分配，避免按 RAWINPUT
  解引用 union 时越界（键盘只有 40 字节，union 按 48 读尾部 8 字节）。
- 新增 `win.rs::raw_input_len_ok(dw_type, dw_size)`：按 dwType 用 `RAWINPUTHEADER.dwSize` 校验。
- `activity.rs::raw_wndproc`：门槛改为「header 可读 + raw_input_len_ok」。
- 新增 2 条测试固化不变量「键盘载荷 < size_of::<RAWINPUT>()」，用相对 size_of 表达，x64/x86 通吃。
- `cargo check` 零警告；`cargo test` 25 passed（原 23 + 新 2）。

**教训**：拆掉低端钩子本身就会让输入法变快，「不卡了」不等于「数据到了」。改采集源后必须逐项
核对每个计数器的非零性，而不是只看体验指标。

## B4：手动改过的加班记录不再被自动锁屏数据静默覆盖（提交 5da4280）

用户从 B3 / B4（+ B4 另一半「不锁屏无记录」）里选了 B4。

**问题**：自动路径 `main.rs` 锁屏 → `calc_record` 与手动路径 `save_manual` 都汇入
`upsert_record` → `INSERT OR REPLACE`。手动把某天改成 21:30（3.5h）后，当晚再锁屏，
自动算的 20:00 / 2h **无条件覆盖**手改值且无提示。

**根因**：`INSERT OR REPLACE` 冲突时是「先 DELETE 再 INSERT」，**无法附加条件**，
所以做不到「手改的不让覆盖」。必须换成 UPSERT。

**修复**：
- `ot_records` 增 `source` 列（0 自动 / 1 手动），`CURRENT_DB_VERSION` 1→2，
  走 `ALTER TABLE ... ADD COLUMN ... NOT NULL DEFAULT 0` 平滑迁移；
- `upsert_record` 拆 `upsert_auto` / `upsert_manual`，共用一条 UPSERT：
  `ON CONFLICT(date) DO UPDATE ... WHERE ?10 <> 0 OR ot_records.source = 0`；
  来源由路径决定、不信任调用方传值；
- `OvertimeRecord.source` 必须 `#[serde(default)]`——旧 `overtime.json` 无此字段，
  否则 `migrate_ot_json` 反序列化整批历史归档直接失败（差点漏掉）；
- 前端加班表 7→8 列加「来源」，手动橙色高亮；
- 缓存戳同步 bump：`styles.css` 12→13、`app.js` 13→14、`index.html` 10→11（tauri.conf.json）、
  `FE_VER` → `2026-09-04.v14`。

**测试**：新增 4 条，覆盖语义用 `Connection::open_in_memory()` + `db::CREATE_OT_RECORDS`
建表验证（**不碰真实 `%APPDATA%/niuma-timer/niuma.db`**）：自动绝不覆盖手动、
自动可覆盖自动、手动可覆盖一切、旧 JSON 无 source 字段仍能反序列化。
为此把 SCHEMA 拆成 `TABLE_DDL` 数组 + `pub(crate) CREATE_OT_RECORDS` 常量
（`concat!` 只吃字面量、组合不了 `const &str`）。

`cargo check` 零警告；`cargo test` **29 passed**（原 25 + 新 4）；`node --check app.js` 通过。

## 部署坑：raw cargo build 的 exe 在干净 Win11 双击无反应（缺 VC++ Redistributable）

用户把最新 `bin/release/niuma-timer.exe` 拷到**全新 Win11 第一次运行**，反馈「点击了啥反应都没有」，疑为首次无数据/初始化 bug。

排查：config::load（默认+建目录）、db::conn（create_dir_all 先于 open + migrate_db 幂等建表）、
holiday 缓存（None→异步拉取）、三个监控 summary（空数据容错）、前端 boot/全局 error 兜底——
**全部对空数据容错，代码与开发机一致，无首跑 panic**。故非逻辑 bug。

根因：`cargo build --release` 默认**动态链接 MSVC CRT**（vcruntime140/msvcp140/ucrtbase），
目标机需装 **Visual C++ Redistributable (x64)**。干净 Win11 不一定带（非 inbox 组件），
缺则 exe 启动失败 → 表现为「双击无反应」。

修复：`src-tauri/.cargo/config.toml` 加 `[build] rustflags=["-C","target-feature=+crt-static"]`
静态链接 CRT；重新编译并覆盖 `bin/release/niuma-timer.exe`。
PE 导入表解析确认：已无 vcruntime140/msvcp140/ucrtbase，仅剩系统 DLL（kernel32/user32/
advapi32/shell32/ws2_32/wtsapi32 等，任意 Win11 必有）。构建耗时约 3 分钟（deps 重编 crt-static）。

仍依赖 **WebView2**（Win11 自带 inbox；若发 Win10/Server 可能需单独装）。
正式分发建议 `tauri build` 出安装包（自带 WebView2 + VC++ bootstrap）；
静态 CRT 已覆盖「缺 VC++ redist」这类场景，直接发 exe 即可在 Win11 跑。

教训：给别人机器直接发 `cargo build` 的 exe 前，要么目标机确认有 VC++ redist，
要么静态链接 CRT，要么出安装包；否则「启动无反应」极易被误判成代码 bug。

## 诊断：进程起来又退出 → 加 panic hook + 启动阶段追踪日志（提交 f178bf8）

用户静态 CRT 版在干净 Win11 仍「双击无反应，感觉进程起来又退出」。

关键判据：「进程起来又退出」= exe 能启动（DLL 不缺 → 静态 CRT 已生效），
是 **main() 启动期 panic** 导致静默退出。release 因 `windows_subsystem="windows"`
无控制台窗口，panic 直接静默退出，旧 `debug.log` 仅前端 JS 写、webview 未起则无日志。

修复（`src-tauri/src/main.rs`）：
- `install_crash_log()`：main() 最开头调用。写 `[start]` 标记到
  `%APPDATA%/niuma-timer/panic.log`，并 `panic::set_hook` 把 panic 信息 +
  `std::backtrace::Backtrace::force_capture()` 追加到同一文件；
- `trace_startup(stage)`：在 setup() 各阶段写「到达 X」痕迹
  （enter / db migrated / app names normalized / holiday cache loaded / window icons set /
  tray created / lock monitor started / monitor switches applied / activity started /
  app_usage started / audio_usage started / done）；build 成功后写「app: built, entering run loop」；
- 把 builder 链开头改成 `let app =`，`.expect("error while building tauri application")` 后
  以 `;` 收尾（**曾误写 `};` 多一个 `}` 导致编译失败**，修掉）。

已提交 f178bf8（与 .cargo/config.toml 静态 CRT 同一次提交）。编译交用户自跑。

**用法（给用户）**：
- 跑 release → 若静默退出，打开 `C:\Users\<你>\AppData\Roaming\niuma-timer\panic.log`，
  最后一条 `[setup: ...]` 之前即崩溃点；有 `[panic]` 即 panic 内容 + backtrace。
- 最快诊断：从 cmd 跑 `bin/debug/niuma-timer.exe`（debug 带控制台子系统），panic 直接打印到终端。

**可能 panic 点（已静态扫描）**：
- build 阶段（只有 `[start]` 无 setup 痕迹，或 `[panic] error while building tauri application`）：
  最可能是 **WebView2 缺失**；其次 generate_context / single-instance 插件。
- setup 阶段：`db.rs:195` `Connection::open(db_path()).expect("无法打开 niuma.db")`、
  `db.rs:150` `execute_batch(ddl).expect("初始化数据库表失败")`、`db.rs:161/165` 迁移/版本 expect、
  `tray.rs::create_tray` 经 `?` 上抛 → `.expect` 同款。
- 其余 `.unwrap()` 多为 Mutex（仅锁中毒 panic，非启动路径）。

## 可见化：build 失败弹窗而非静默退出（提交 96f6839）

接着 f178bf8 继续推：既然「进程起来又退出」多半是启动期出错被吞，把 **build 失败也变可见**。

`main.rs`：把 `.build(tauri::generate_context!()).expect("error while building tauri application")`
改为 `match app`——
- `Ok(app)` → 照旧 `app.run(...)`；
- `Err(e)` → `show_fatal(&msg)` 弹 `MessageBoxW`(MB_OK|MB_ICONERROR) + 写 `[fatal]` 到 panic.log
  后 `std::process::exit(1)`。错误信息含 `webview` 关键字时追加「缺 WebView2 运行时」安装指引
  （Evergreen Bootstrapper）。

现在干净 Win11 首跑的两类静默退出都有出口：
- build 阶段失败（最可能是缺 WebView2）→ 弹窗直接说原因；
- setup/run 阶段 panic → panic hook 写 panic.log（release 无声、debug 打终端）。

`cargo check --offline` 零警告。编译交用户自跑（不替他 build）。

## 真因锁定：全新库「duplicate column name: source」panic（提交 9f09dcd）

用户从干净 Win11 拷回 `panic.log`（bin/panic.log）：
`[start] → [app: built] → [setup: enter] → [panic] src\db.rs:161 迁移 ot_records 失败:
duplicate column name: source`。

**根因**：`CREATE_OT_RECORDS` 建表 DDL 已含 `source` 列（v2 schema），而 `migrate_db`
的 `version<2` 分支又无条件 `ALTER TABLE ot_records ADD COLUMN source` → 全新库（version=0）
建表即带 source、再 ALTER 重复加列 → panic。dev 机不崩：库早是 v2，`version>=2` 直接 return，
迁移从不触发，只在干净机器首跑暴露。

**修法**（db.rs）：v2 迁移前用 `pragma_table_info('ot_records')` 查 source 是否存在，
仅旧库（无该列）才 ALTER，全新库跳过。保留 CREATE_OT_RECORDS 含 source（overtime.rs 的
upsert INSERT 硬依赖该列、单测也靠它建表，不能删）。

**回归测试**：加 `db::tests::migrate_fresh_db_does_not_duplicate_source` 与
`migrate_v1_db_adds_source`（in-memory，不碰真实库），分别校验全新库跳过 ALTER、v1 旧库升级补齐 source。

`cargo test --offline` **31 passed**（原 29 + 新 2）。三连提交：f178bf8(崩溃日志) /
96f6839(build 失败弹窗) / 9f09dcd(迁移修 panic)。干净机器首跑崩溃链已闭合。

**遗留**：panic.log / show_fatal 的弹窗能力仍可保留（部署诊断有价值）；下一步回到「下一个优化」
（app_usage 前台窗口钩子收编进 win.rs 等痛点 #2 债，或 audio_usage WASAPI 收编）。
